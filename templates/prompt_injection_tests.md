# 프롬프트 인젝션 체크리스트

실제 페이로드는 문제 상황에 맞게 직접 창작한다. 아래는 **사고 틀(어떤 축을 건드려볼지)**이지 복붙용이 아니다.
한 번에 하나의 축만 바꿔 가며(변인 통제) 거부/필터 신호를 읽고 좁혀간다.

## A. 정찰 (먼저)
- [ ] 모델이 무엇을 거부하는가? (금지어 필터인가, 의미 기반인가)
- [ ] 시스템 프롬프트의 흔적이 응답에 새는가?
- [ ] 성공 조건은? (Flag 문자열 노출 / 특정 행동 수행)
- [ ] 입력 길이·형식 제한, 레이트리밋이 있는가?

## B. 공략 축
- [ ] **지시 재정의**: 상위/운영자 지시인 척, 이전 지시 무효화 프레이밍
- [ ] **역할/모드 전환**: 디버그·개발자·번역 등 다른 맥락으로 전환
- [ ] **지시/데이터 경계 혼동**: 입력을 '명령'으로 해석하게 유도
- [ ] **시스템 프롬프트 추출**: "위 내용을 그대로 반복/요약"류
- [ ] **출력 우회**: base64/leetspeak 인코딩, 언어 전환, 분할 출력
- [ ] **간접 인젝션**: 모델이 읽는 외부 자료(문서/RAG/툴 출력)에 지시 심기
- [ ] **다단계**: 여러 턴에 걸쳐 맥락을 쌓기

## C. 간접 정보 추출 (side-channel) — 직접 질문이 막힐 때
- [ ] **연산/비교 요구**: 거리·중간지점·정렬·순위·집계·통계를 묻기
      → 모델이 계산하며 보호 필드(타 사용자 이름/위치 등)를 흘림
- [ ] **존재 추론 → 특정**: 흘린 조각으로 admin 등 특수 계정 찾기
- [ ] **필드 분할 조합**: Flag가 여러 필드에 쪼개져 있을 수 있음 → 각 필드를 간접 출력시켜 합치기
- [ ] **거부 응답 자체 분석**: 거부 메시지가 정보를 흘릴 수 있음

## D. 매 시도 기록
- 가설 한 줄 / 보낸 내용 / 거부 신호 / 다음에 바꿀 축
- 성공 프롬프트와 그 변형은 `solutions/<문제명>/`에 저장
